Purpose

Convert a five-month-old, organically adopted skill into a small but professionally maintained public release without losing the direct promise that attracted users: one YouTube link becomes one useful Markdown knowledge note.

Problem

The release is ready and selective distribution has begun. The real risk remains channel quality: some libraries prohibit AI-created submissions, one large list has hundreds of open pull requests, two newer registries have broken or unavailable source paths, and copy-based catalogs would create a second skill source that can drift. CodeGuilds remains a separate installer blocker rather than a reason to delay trustworthy link-based catalogs.

Current evidence: 191 GitHub stars, 15 forks, 118 deduplicated skills.sh installs, 280 views from 122 visitors, and 278 clones from 149 cloners in the available GitHub traffic window. The public v1.1.0 release, CI, isolated installation, and live transcript smoke are complete. VoltAgent pull request #869 is the only new directory submission.

Solution

Run distribution as a gated funnel: refresh the evidence and policies, submit first to the strongest link-based catalog, preserve human authorship where required, hold channels whose fit or provenance is doubtful, verify every accepted listing, and measure four weeks before expanding.

Success Contract

User outcome

A user can install the complete skill, provide a supported YouTube link, and receive a correctly labeled, queryable Markdown note in the expected location without an API key or an unexpected overwrite.

Acceptance criteria

The completed v1.1 checks remain green. Before each external action, the current channel policy, duplicate state, released URL, and public install are rechecked. Human-only submissions are written and sent by Jimmy. Every accepted listing resolves to the canonical repository, and distribution results are recorded for four weeks.

Invariants

GitHub remains the canonical source. The default result remains a single local Markdown archival note with transcript, creator description, chapters when available, metadata, and capture provenance. No API key is required. Existing user files are not silently overwritten.

Non-goals

No feature race, paid promotion, social-media campaign, mass directory blast, directory-specific fork, copied skill bundle, or product change made only to satisfy a catalog.

Failure conditions

The plan fails if an external action occurs without its approval, Codex authors or submits where a maintainer requires a human, a listing copies the skill without an approved synchronization model, CodeGuilds receives a trust badge while its installer fails, a submission overstates Claude-specific functionality, or adoption is claimed without direct evidence.

Questionables

  1. Questionable 1: Should a bare YouTube link immediately create a file?

    Recommendation for v1.1: preserve the current behavior because it is part of the simple viral promise, but make the skill state the save location clearly and never use --force automatically. If Jimmy prefers an intent question for bare links, amend Phase 1 before build.

  2. Questionable 2 — resolved: Should Python 3.8 remain supported?

    Decision: yes. The implementation uses deferred annotations, the declared dependency ranges support Python 3.8, and all fourteen tests plus compilation passed on disposable CPython 3.8.20. CI will repeat the proof after publication approval.

  3. Questionable 3 — resolved: Should the repository rename master to main?

    Decision: yes. The last-minute audit discovered that CodeGuilds mixed a raw main banner with a raw master README, and GitHub does not redirect raw branch URLs. The repository therefore uses canonical main plus an automatically fast-forwarded master compatibility branch. Both raw routes resolve, local tracking moved cleanly, the registered worktree was preserved, and the synchronization workflow passed after merge.

  4. Questionable 4: Should v1.1 add speaker identification, translation, cover images, or caching to compete with the 18.3k-install leader?

    Recommendation: no. Those features would blur the release and make review harder. Compete through a smaller, dependable, single-file archival-note experience. Reconsider advanced features only after observing user requests after v1.1.

  5. Questionable 5: Should CodeGuilds receive a badge immediately because the listing is claimed?

    Recommendation: no. Keep the claimed page, fix its metadata, and add the badge only after its published installer successfully copies and runs the full skill in isolation.

  6. Questionable 6: Should the skill be copied into large community repositories?

    Recommendation: prefer link-based catalogs. A copied skill becomes a second source that can miss fixes and dependency updates. Consider vendoring only when a directory proves meaningful reach and has an explicit upstream synchronization model.

  7. Questionable 7: Should the skill be recommended to Awesome Claude Code now?

    Recommendation: hold. Recommendations are open, but the human web form requires Jimmy to attest that the resource is specific to Claude Code. The released skill is intentionally cross-agent and does not currently prove unique Claude Code functionality. Reach does not justify a doubtful attestation.
